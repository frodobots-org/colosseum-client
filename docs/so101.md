# SO-ARM101

This Client implementation targets **one SO-ARM101 follower arm** driven through
[LeRobot](https://github.com/huggingface/lerobot)'s `so101_follower` Feetech
driver, with cameras opened through LeRobot's RealSense and OpenCV drivers.
It does not support the leader arm, bimanual setups or other servo firmware.
Software tests use a fake follower; closed-loop task performance depends on your
rig, calibration and the model served by the Policy Server.

## Contract

- `robot_type: so101`, absolute `joint_position`, 6 values.
- Action/state order: `shoulder_pan, shoulder_lift, elbow_flex, wrist_flex,
  wrist_roll, gripper`. This is LeRobot's `so101_follower` convention with
  `use_degrees=True`: joint angles are **degrees** relative to the calibrated
  mid-range, and the gripper is its opening in **[0, 100]** (0 closed, 100 open).
  Values are neither converted to radians nor binarized.
- Transport observations split `joint_position` into five values and
  `gripper_position` into one. LeRobot export concatenates them again and names
  the dimensions `shoulder_pan.pos` ... `gripper.pos`, matching datasets recorded
  with `lerobot-record`.
- Camera roles follow the Router task (`head_image`, `left_image`, `right_image`).
  A typical rig uses `head_image` for the fixed top/front camera and `left_image`
  for the wrist camera. Images are RGB uint8; cameras capture 640x480 at 30 FPS
  by default and are resized only if `image_width`/`image_height` differ.
  Each observation uses the latest frame from every camera; cameras are not
  hardware synchronized.
- Cartesian pose is unavailable: the driver returns an empty vector and export
  omits `observation.cartesian_position`. It never fabricates a zero pose.
- The control rate is not fixed by the driver. Set `control_hz` to the rate of
  the models registered for SO101 on your Router (LeRobot datasets commonly use 30).

## Install and configure the robot host

LeRobot requires Python 3.12 or newer. From the `colosseum-client` checkout:

```bash
uv sync --python 3.12 --extra so101
cp configs/robot.so101.yaml.example configs/robot.so101.yaml
```

Install ffmpeg for recording/export and ffprobe for video tests. Calibrate the arm once with LeRobot, using
the same id you put in `adapter_config.robot_id`:

```bash
.venv/bin/lerobot-calibrate --robot.type=so101_follower --robot.port=/dev/ttyACM0 --robot.id=follower_arm
```

The driver never starts LeRobot's interactive calibration: an uncalibrated arm,
or one whose stored motor calibration differs from the calibration file, fails
at start-up instead.

Fill in the Router URL/token, serial port, camera IDs and the two five-element
arrays `joint_low` and `joint_high` in degrees. Placeholder nulls deliberately
fail before opening hardware. A numeric ID longer than four digits is opened as
a RealSense serial; anything else is a V4L2 index or path. Set
`adapter_config.camera_types` to override that.

## Motion and shutdown behavior

- Malformed and nonfinite actions are rejected before any motor command.
- Joint targets are **clamped** to `[joint_low, joint_high]` and the gripper to
  `[0, 100]`. Learned policies often overshoot a calibrated end stop by a
  fraction of a degree; rejecting those would abort trials that are otherwise
  valid. Recorded actions are the model's commands before clamping.
- Optional `max_relative_target` uses LeRobot's limit: a command further than
  that many degrees from the measured position is shortened, not rejected.
- Starting a trial enables motor torque at the current pose. The driver does not
  home the arm: place it in its rest pose before confirming each trial.
- Optional `start_poses` moves the arm to a fixed pose before a given model
  takes over, in steps of at most `return_step_deg`. Keys are matched against
  the assigned model's `runtime_profile`, `subfolder` or `url`; models without an
  entry start where the arm is. This exists because some checkpoints are
  deployed upstream from a home pose (G05's SO100 client homes to the
  training-data mean) and degrade from a folded rest pose. It applies to local
  inference with action execution enabled, and it changes the evaluation
  conditions for that model, so record it in `scene` when you use it.
- At the end of a trial, including after errors and Ctrl-C, the arm moves back
  to the pose measured at start-up in steps of at most `return_step_deg`, then
  releases torque. Set `return_to_start: false` to release torque where the arm
  stopped; an unsupported arm will then drop under gravity.
- A gripper that squeezes an object long enough trips its overload protection,
  and the servo then answers every command with an Overload alarm. LeRobot's
  disconnect stops at that alarm, before the port and cameras. The driver then
  writes torque off to every motor, confirms it with a read-back, and releases
  the port and cameras. If torque is confirmed off, the alarm is logged as a
  warning and the evaluation continues; otherwise the trial fails as before.

- A serial bus error while connecting (Feetech buses occasionally corrupt a
  status packet) is retried up to three times; each failed attempt disables
  torque and releases the port and cameras first.

## Run

```bash
uv run --no-sync colosseum-robot configs/robot.so101.yaml --no-execute-action
# After checking observations and the returned actions:
uv run --no-sync colosseum-robot configs/robot.so101.yaml
```

`--no-execute-action` still enables torque, reads the arm and cameras and
requests inference; only the model's commands are skipped.

Local Policy evaluation is enabled for `so101` with the 6-value
`joint_position` contract. The Policy Server needs a model adapter that supports
`robot_type: so101`, and the Router needs matching model registrations; this
driver does not provide either.

### Eval station (GUI)

One command runs setup checks, A/B recording and review in the browser; it is the same Eval Station as
the YAM rig's, with SO101 checks (USB link, read-only arm and calibration check, LeRobot cameras):

```bash
uv pip install --python .venv/bin/python -e '.[gui]'   # once: fastapi, uvicorn, anthropic
.venv/bin/python scripts/eval_gui.py                    # defaults: configs/robot.so101.yaml and
                                                        # ../colosseum-policy-server/configs/local-runtime-so101.yaml
# open http://127.0.0.1:8770
```

- **Setup** checks the GPU, the arm's USB link, the motors and their calibration (torque untouched),
  both cameras (and ffmpeg, which recording needs), the Router, API keys and the Policy Server.
- **Record** requests a Router A/B eval with a live top-camera view. The client's prompts appear as
  dialogs; **STOP POLICY** (or Esc) ends the run as unsafe and **Task done** ends it as done. Either
  way the recording is kept, the arm holds its measured pose, then returns to its start pose.
- **Review** shows both runs' videos side by side for scoring, factor comparison and preference;
  Claude Haiku can draft the feedback (an Anthropic key or the Claude Code login). Nothing is uploaded
  before **Submit to Router**.
- **Offline** (header switch or `--offline`): no Router; each eval picks two local policies at random,
  nothing is uploaded, and the policies are revealed after the result is kept.

Ctrl-C ends any active run through the normal client path, then stops the Policy Server it started.

## LLM EEF control in mixed evaluations

Install the SO101 EEF extra before starting this mode; it adds LeRobot's Placo
IK dependencies to the normal follower and camera drivers:

```bash
uv sync --python 3.12 --locked --extra so101-eef
```

Use [robot.so101.eef.yaml.example](../configs/robot.so101.eef.yaml.example) with
the mixed Policy Server configuration. Keep `llm_control_mode: eef_delta_pose`:
Router-assigned LLMs then receive measured EEF state and issue base-frame
EEF deltas. Router-assigned VLAs still use the normal six-value joint-position
path. Set `adapter_config.eef_urdf_path` to the calibrated SO101 URDF with a
`gripper_frame_link`, and set `max_relative_target: null` to disable LeRobot's
additional per-command displacement clamp.
For each LLM trial, the Client uses the assigned Router model's `control_hz`
for action pacing and recording FPS. `control_hz` in the Client config remains
the VLA rate.

EEF target motion is divided over the requested number of steps, bounded by
the Router-assigned `max_horizon`. There is no additional EEF displacement
or gripper step cap. The Client solves IK from measured joint positions
and records the joint command accepted by LeRobot in the existing LeRobot dataset. `eef-actions.jsonl` alongside the
recording keeps the EEF deltas for diagnosis. Evaluation scores and dataset
upload continue through this repository's existing Router flow.

IK solutions within 0.0001° of a calibrated joint limit are clamped to that
limit to absorb numerical roundoff. If a solution exceeds that tolerance, the
Client logs the offending joint, commands a hold at the measured pose, records
that accepted hold command, and continues the trial. The rejected EEF delta,
including its gripper component, is not applied to later steps in the chunk.
An unsafe measured joint state or a motor communication failure still stops the
trial.

The EEF path requires action execution to record accepted joint commands, so
`--no-execute-action` is unavailable for EEF-assigned trials. Test with the
synthetic `test: true` configuration before connecting hardware. Software tests
do not establish physical tracking quality or task success.

## Depth for CaP-X models

A Policy Server CaP-X model, named `<llm>-capx` (for example `claude-opus-5-5-capx`; see the Policy Server's
`docs/inspect-capx.md`) can ask for depth in its ready message. Only then does
the Client enable the depth stream of one RealSense camera and align it to that
camera's color image. Each observation then carries two extra state tensors:
`<role>_depth_m` (H x W float32 metres at the sent image size) and
`<role>_intrinsics` (3 x 3, scaled to the same size). Depth is sent only to the
Policy Server. Recordings, LeRobot exports and dataset uploads never include it.

The camera defaults to the first RealSense role in `cameras`. Set
`adapter_config.depth_camera` to pick another one, which must also be a
RealSense role. The stream must be unrotated. A trial that asks for depth fails
at start-up if no usable RealSense camera is configured. YAM streams depth
too (see `docs/yam.md`); other robot types reject the request. CaP-X models always use the six-value joint-position path,
even under `llm_control_mode: eef_delta_pose`, because the Policy Server solves
their IK.
